Counting alerts and counting failing devices are different questions, and during
an incident only the second one tells you how much of the fleet is affected. This
article follows that second number through a streaming pipeline on Google Cloud,
from the Beam window where repeated alerts collapse to the BigQuery view where the
HLL++ sketch is built. The placement of that sketch is not a matter of preference:
one line in the documentation for incremental materialized views decides it,
several stages upstream of the query that needs the answer.

## A hundred thousand alerts, but how many failing devices?

Imagine monitoring an IoT fleet emitting 100,000 failure alerts every minute. Your real-time monitoring dashboard spikes red. Before alerting on-call field technicians, you need to answer a fundamental question: **Are 100,000 distinct devices failing, or is a single broken device spamming the pipeline 100,000 times?**

The former represents a fleet-wide outage; the latter is a routine hardware swap. Yet, if your dashboard queries are based on `COUNT(*)`, both scenarios will look identical.

What we are dealing with here is **cardinality estimation** under high-throughput streaming constraints. Measuring page views vs. unique visitors, or API errors vs. impacted customers, shares this exact structure.

> The pipeline code, the SQL, and the unit tests live in the [`eventually-consistent/counting-failing-devices`](https://github.com/ggasg/eventually-consistent/tree/main/counting-failing-devices) repository.

## Stream processing vs. Batch queries

In a standard batch processing world, answering unique device counts is simple:
```sql
SELECT COUNT(DISTINCT device_id) 
FROM telemetry.alerts 
WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR);
```

In a real-time streaming architecture, however, data never stops arriving. Streams are unbounded, and records can (and will) arrive out of order due to a wide variety of reasons like network latency, retries, flaky connections, or lower level middleware GC pauses.

To handle streaming inputs, Data Engineers may choose to partition data into **fixed-time windows** (e.g., 1-minute tumbling windows). Streaming Frameworks like Flink or Spark Structured Streaming (to an extent) manage late-arriving events via **watermarks**, the streaming engine’s dynamic progress estimator. When a watermark passes the boundary of a window, the pipeline materializes the aggregated result.

### Memory vs. Precision: The HyperLogLog++ Sketch

Tracking exact unique device IDs requires maintaining a set in memory. For a few thousand devices, this is trivial. For hundreds of millions of unique entities, maintaining set state inside streaming worker memory leads to memory pressure and high processing latency.

A sketch is a compact summary of an aggregation that keeps enough information to extract a result, to carry on aggregating, or to be merged with another sketch of the same kind. BigQuery ships two families, HLL++ for distinct counts and KLL for quantiles, and documents both on its [sketches page](https://cloud.google.com/bigquery/docs/sketches).

For distinct counts, the trade is exactness for a bounded memory footprint:

* **HyperLogLog++** maps inputs into an array of small integer registers (32,768 registers at BigQuery's default settings, consuming roughly 32 KB).
* **Deterministic Bounds:** at its default precision, BigQuery [documents](https://cloud.google.com/bigquery/docs/sketches) an error margin of **±1.15% at 95% confidence** and **±1.72% at 99% confidence**. The algorithm itself is [HyperLogLog in Practice](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/40671.pdf), by Heule, Nunkesser and Hall, 2013.
* **Key Properties:**
  1. **Constant Size:** Memory footprint remains 32 KB whether tracking 10 or 10,000,000 distinct IDs.
  2. **Mergeability:** Two independent sketches built over disjoint time intervals can be combined (via bitwise maximum per register) to yield the exact sketch that would have been produced by evaluating all inputs at once.

### In-Memory Deduplication with Apache Beam

In our pipeline, Apache Beam performs localized deduplication within a tumbling window using a custom `CombineFn`. If a device breaches an alarm threshold 50 times in a single minute, Dataflow emits its ID exactly once per window:

```python
import apache_beam as beam

class DistinctDeviceIdsCombineFn(beam.CombineFn):
    def create_accumulator(self):
        return set()

    def add_input(self, accumulator, device_id):
        if device_id:
            accumulator.add(str(device_id))
        return accumulator

    def merge_accumulators(self, accumulators):
        merged = set()
        for acc in accumulators:
            merged.update(acc)
        return merged

    def extract_output(self, accumulator):
        return sorted(accumulator)
```

The accumulator is a `set`, so adding a device ID that is already present leaves it unchanged. The payload leaving each window therefore scales with the number of **unique failing devices per minute**, and the message rate never enters into it.

## Deciding Where to Initialize the Sketch

An intuitive optimization would be generating the HLL++ sketch directly inside the Apache Beam pipeline, emitting binary sketch payloads to BigQuery. However, BigQuery Materialized View semantics force a different architectural decision.

BigQuery Materialized Views maintain incremental state as new rows land in underlying tables. To support zero-cost incremental maintenance, [BigQuery restricts the supported aggregation functions](https://cloud.google.com/bigquery/docs/materialized-views-create):

<Note title="Supported aggregations in materialized views">
`ANY_VALUE`, `APPROX_COUNT_DISTINCT`, `ARRAY_AGG`, `AVG`, `BIT_AND`, `BIT_OR`, `BIT_XOR`, `COUNT`, `COUNTIF`, `HLL_COUNT.INIT`, `LOGICAL_AND`, `LOGICAL_OR`, `MAX`, `MIN`, `MAX_BY`, `MIN_BY`, `SUM`
</Note>

Crucially, **`HLL_COUNT.INIT`** is supported, but **`HLL_COUNT.MERGE`** is not. 

If Apache Beam emits pre-aggregated sketch binaries, BigQuery cannot incrementally merge them in a Materialized View without doing a full table re-scan. Therefore, **the pipeline must emit raw arrays of distinct device IDs (`ARRAY<STRING>`), delegating sketch initialization to BigQuery's native materialized engine:**

```sql
CREATE MATERIALIZED VIEW iot_analytics.hourly_anomaly_rollup AS
SELECT
  TIMESTAMP_TRUNC(window_timestamp, HOUR) AS hourly_bucket,
  sensor_type,
  HLL_COUNT.INIT(device_id) AS intermediate_sketch
FROM iot_analytics.raw_anomaly_device_ids, UNNEST(device_ids) AS device_id
GROUP BY 1, 2;
```

## Storing a Count Instead of a Sketch

The obvious design does not involve sketches at all, and it is simpler in every visible way.

`APPROX_COUNT_DISTINCT` appears on the supported list above, so a Materialized View can maintain one integer per hourly bucket. That column costs eight bytes per group rather than 32 KB, it holds a number an engineer can read straight off the console instead of opaque `BYTES`, and any BI tool can aggregate it without knowing what a sketch is. It also dissolves the upstream question from the previous section: a view that only needs a count can be fed a count, so nothing forces the Beam pipeline to ship arrays of device IDs at all.

For the question it was built for, it is also correct. Asked how many distinct devices were in alarm during a given hour, the stored integer is the right answer, and it is cheaper to reach than the sketch.

The limit appears as soon as a question crosses a bucket boundary. Adding twenty-four hourly counts together counts each device once for every hour in which it appeared, so a device that stays in alarm all day contributes twenty-four times rather than once. This is not approximation error, and a more accurate estimator would not help. An `INT64` records how many devices there were and nothing about which ones, so two of them cannot be combined without double-counting whatever they have in common.

Merging sketches at read time answers the spanning question without that defect, because the register array still carries enough to tell a repeat from a new device:

```sql
SELECT
  sensor_type,
  HLL_COUNT.MERGE(intermediate_sketch) AS distinct_failing_devices
FROM iot_analytics.hourly_anomaly_rollup
WHERE hourly_bucket >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)
GROUP BY sensor_type;
```

Because merging HLL++ sketches is associative and commutative, unit tests confirm that merging hourly sketches produces the exact same estimate as sketching the entire range at once:

```python
def test_merge_matches_counting_the_union_directly():
    """Merging per-hour sketches gives the same answer as sketching the whole range."""
    hours = [sketch_of(ids(h * 900, h * 900 + 1_500)) for h in range(24)]
    merged = merge_all(hours)
    direct = sketch_of(ids(0, 23 * 900 + 1_500))
    assert merged.estimate() == direct.estimate()
```

## Key takeaways

**Recognise a cardinality problem.** If one participant gets ten times noisier and
your number moves, you are counting events rather than things. That is the signal,
and it arrives long before anyone says the word cardinality.

**Decide what the stored column has to answer.** An integer answers the question it
was aggregated for and nothing wider, because it records how many there were and
not which ones. A sketch costs 32 KB per group and keeps enough to be combined with
another, which is what a question spanning buckets requires. Pick before the column
type is set, not after the first twenty-four-hour query comes back wrong.

**Let the refresh mechanism place the aggregation.** An incremental materialized
view can initialise a sketch but cannot merge one. That single restriction is what
pushes sketch construction into BigQuery and keeps the Beam pipeline emitting arrays
of device IDs, and it is worth checking the equivalent restriction in whatever
maintains your own state before designing the stage that feeds it.
